Tutorial

First capture to first report

This tutorial shows you how to make your first BACcheck report. You need a BACnet/IP capture file. The file must end in .pcap or .pcapng.

1. Install BACcheck

Download the baccheck binary for your system. Put it on your PATH.

2. Run BACcheck on your capture

Open a terminal. Run this command:

baccheck plant-floor-chiller-loop.pcapng

BACcheck reads the file. It writes a report next to it, named plant-floor-chiller-loop.baccheck.html.

3. Open the report

Open the report file in a web browser. The top of the report states the number of findings and the worst severity. Read the summary first.

4. Work the fix list

  1. Find the fix-list table below the summary.
  2. Start at the top row. Rows are ordered by severity, most severe first.
  3. Click a finding's name to open its full detail: affected devices, evidence, and steps to fix it.
  4. Mark a row done when you finish it.

You made your first report. See Read a finding for what each part of a finding means.

How-to guide

Run a capture

Use this guide to record a BACnet/IP capture with a packet-capture tool, ready for BACcheck.

  1. Connect your laptop to the BACnet/IP segment you want to check.
  2. Start your capture tool. Filter on UDP port 47808.
  3. Record for at least 5 minutes. Some BACcheck rules need this much time to raise a finding.
  4. Stop the capture. Save it as .pcap or .pcapng.

How-to guide

Read a finding

Use this guide to read one finding in a BACcheck report.

  1. Read the severity tag. It tells you how urgent the finding is. See Severity levels.
  2. Read the "Affected" line. It names the device or devices involved.
  3. Read the evidence text. It states what BACcheck saw in the capture.
  4. Read the frame numbers. Open your capture tool and jump to these frames to see the raw packets.
  5. Read "What to do". Follow the numbered steps in order.

How-to guide

Apply a remediation

Use this guide to fix a finding using its remediation steps.

  1. Open the finding's "What to do" section.
  2. Complete each numbered step in order. Do not skip a step.
  3. Make one change at a time on the physical device or network.
  4. Record a new capture after you finish all steps.
  5. Run BACcheck again on the new capture. Confirm the finding no longer appears.

How-to guide

Interpret severity

Use this guide to decide which findings to fix first.

  1. Fix every Critical finding first. These stop the network from working correctly right now.
  2. Fix High findings next. These degrade the network under normal conditions.
  3. Schedule Medium findings for your next planned visit.
  4. Note Low findings. Fix them when you are already working on the same device.

Reference

Finding & Report schema

A finding has one issue id, one severity, one or more affected devices, an occurrence count, evidence text, up to 5 example frame numbers, and first/last-seen timestamps.

A report is a flat, ordered list of findings. The order is: severity, then issue, then device. A report also has summary stats and, when more than half the capture is undecodable, a capture-health warning.

Reference

Severity levels

BACcheck uses four severity levels: Critical, High, Medium, Low. A rule may raise a finding's severity above its base level when the evidence is more extreme. A rule never lowers a finding's severity below its base level.

Reference

Evidence-floor semantics

Each detection rule has a minimum amount of evidence it needs before it may raise a finding. This is the rule's evidence floor. Below the floor, the rule stays silent. Rate-based rules also need a minimum capture length of 5 minutes.

Explanation

How the detectors work

Each of the 10 detectors is an independent function. It reads the full stream of decoded BACnet records once, in order, and produces zero or more findings. A detector keeps its own local state as it reads — for example, a table of which device instances have answered which Who-Is. Detectors do not share state or a common pre-pass; this keeps each one simple to test on its own against a fixture capture.

Explanation

BACnet/IP in brief

BACnet is a protocol for building-automation devices — things like chillers, air handlers, and lighting controllers — to talk to each other. BACnet/IP is the variant that runs over ordinary IP networks, using UDP port 47808. Devices announce themselves with a Who-Is/I-Am handshake, and read or write each other's properties with services like ReadProperty. BACcheck only looks at BACnet/IP traffic; it does not look at MS/TP or other BACnet link layers.

Explanation

Why evidence floors exist

A short, quiet capture can look identical to a healthy network and to a network with an intermittent problem — there just isn't enough evidence yet to tell the two apart. Evidence floors stop BACcheck from guessing in that gap: a rule stays silent rather than raising a finding it can't actually support. This keeps every finding in a report backed by enough evidence to act on, at the cost of occasionally under-reporting a real but rarely-triggered problem in a short capture.
